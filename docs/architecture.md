# 架构与数据流

> 本文是整个项目的**最高约定**。代码与本文冲突时，以本文为准；
> 要改架构，**先改本文**。

**项目名**：`webgal-screenplay-compiler`。`compiler/` 负责剧本编译，`production/` 负责演出组装、可回退安装和交付验收。

---

## 一、第一条：本项目**适配** WebGAL，不做渲染

### 分工

| 层 | 职责 | 归属 |
|---|---|---|
| **渲染与演出层** | PixiJS 舞台、立绘、Live2D、Spine、滤镜、动画、转场、存档、鉴赏、流程图、UI | **WebGAL**（上游，不重写） |
| **编译层** | 剧本 → WebGAL 原生场景文件 | **`compiler/`**（本项目） |
| **生产层** | 原生场景与素材 → 可验收、可回退的游戏交付物 | **`production/`**（Codex 阶段提取） |

一句话：**WebGAL 是引擎，本项目是它的上游。**

### 为什么这么分（依据，不是偏好）

1. **WebGAL 是这个领域最成熟的开源 VN 引擎**：PixiJS 6 + React 17 渲染、37 条演出指令、
   Live2D / Spine 支持、30+ 滤镜、存档 / 鉴赏 / 流程图、图形化编辑器。
   这些**自研追不上，也不该追**。
2. **但 WebGAL 不含「剧本 → 场景文件」的编译工具链。** 它的作者侧入口是图形编辑器，
   一屏一屏摆。要把一份**已有的文字剧本**搬进去，中间这段自动化得自己做。
   **这是本项目存在的理由。**

### 由此推出的判断标准

- ✅ 改进编译链、加剧本规范检查、打磨断框与资源映射
- ✅ 研究 WebGAL 的指令能力并**用它**（学它的语法与坑，设计自己的降级方案）
- ✅ 产出可复用的 WebGAL 资源与工具
- ❌ 重写 Pixi 舞台 / UI / 特效 / 存档系统
- ❌ 把本项目做成「不依赖 WebGAL 也能跑」的独立渲染器
- ❌ fork WebGAL 源码做侵入式修改（**配置与脚本能解决的事不要改源码**）

## 二、交付以**编译期落盘的原生场景文件**为基础

产物是**静态文件**，写进上游 WebGAL 的 `game/` 目录，靠**官方「开始游戏」入口**进入。
默认编译链与原生导入模式无需本项目的客户端运行时代码。

生产层另提供显式启用的章节自动存档扩展：基于 WebGAL 4.6.5 中文原生菜单和舞台快照，操作原生八槽存档，不写私有存档格式。它有自己的运行时、CSS 和本地预览连接，需按 [接驳说明](production-integration.md) 验收；关闭时仍可原生手动存档。两种模式都从 `start.txt` 播放，不发送剧情注入命令，也不修改引擎 bundle。

接驳点是 `compiler/build-demo.mjs` 已生成的整个 `game/` 目录。生产层默认逐字节保留正文、分支、配乐、配置和主题，生成自有清单后由安装器覆盖到另一份 WebGAL 发行目录；不根据拍下标重新推断人物或改写分支。数据化演出工程也可直接使用生产层的项目契约。

### 为什么不走「运行时注入」

WebGAL 上游确实内置一套**编辑器实时预览协议**
（`webgal-editor-preview-sync.v1`），`preview.command.run-scene-content` 能把任意脚本文本
直接解析成当前场景、**不要求落盘**。所以「每一拍调一次模型、把结果推上舞台」技术上可行。

**本项目探索过，没有采用**，因为它要付三个代价：

| 代价 | 说明 |
|---|---|
| **玩家端不再零改动** | 落盘方案里 WebGAL 一个字节都不用改；注入方案要你在 `index.html` 里插脚本（预置语言等引擎前置条件） |
| **运行时多了自己那层代码** | 落盘方案的运行时是 WebGAL 自己；注入方案的运行时是**你自己写的服务**——它卡住，玩家看到的就是「加载中」 |
| **产物进不了引擎的原生系统** | 注入的拍用不了存档 / 回廊 / 鉴赏 / 流程图；且 `run-scene-content` 每拍 `resetStage`，舞台连续性要自己拿「舞台记忆」补 |

⇒ **要引入运行时注入，先改本文，并准备好承担上面三条。** 别把它当成一条「顺手也能加」的支线。

> 那套协议的字段、注册方向与如实记录的代价，见
> [`webgal-redlines.md`](webgal-redlines.md) §3.6 —— **调研结论保留，代码不在本仓**。

## 三、从剧本到可玩：编译链

```
docx（说话人已标注）
   │  extract-docx.py            docx → 结构化 JSON
   ▼
script.json
   │  docx-to-mainline.mjs       角色表 + 模式规则 + 文本框切分
   ▼
mainline/beats.json              可渲染的一拍一拍
   │  build-demo.mjs             章节卡 / 分支跳转 / 配乐落点 / config.txt
   ▼
WebGAL 场景文件（原生模式）→ webgal-tool/dist/game/
```

配套的规则模块（**都在编译期被 `build-demo.mjs` 调用，运行时一律不生效**）：

| 模块 | 管什么 | 出厂状态 |
|---|---|---|
| `text-split.mjs` + `textbox.mjs` | 断框切分与容量阈值（**唯一实现**） | 可用 |
| `editorial.mjs` | 编辑层表述识别（预告 / 卷末旗标） | 可用 |
| `anchor.mjs` | 剧情锚点（按内容子串匹配，不依赖断框） | 可用 |
| `branches.mjs` + `verify-branch.mjs` | 分支数据源与悬空跳转体检 | 示例数据 |
| `bg-rules.mjs` | 场景 → 背景图（**必须与 `demo-assets.mjs` 的产物同名对齐**） | 可用 |
| `sfx-rules.mjs` + `sfx-catalog.json` | 文本 → 音效（25 单发 + 17 环境） | 可用 |
| `bgm-cues.mjs` | 场景 → 配乐落点 | ⚠️ **`SCENE_CUE` 出厂为空，必须先填** |
| `demo-assets.mjs` | 占位背景与立绘（纯 Node 手写 PNG） | 可用 |
| `check-syntax.mjs` | 产物语法体检 | 可用 |
| `screenplay.mjs` | 剧本规范体检器（7 类检查） | 可用 |

### 三条不可违反的编译期约束

1. **链序不能乱。** 中间任何一步改了切分或编号，下游全部失效且**不一定报错**——
   这是本项目最贵的一类 bug，详见 [`pitfalls.md`](pitfalls.md) 第 2 条。
2. **资源名即契约。** 立绘 `{id}.png` · 背景 `bg_{place}.png` · 音效 `{id}.wav`——
   规则表与生成器**同名对齐**，对不上的表现是**画面静默空白**，不是报错。
3. **同一份规则只能有一处实现。** 切分只有 `text-split.mjs`，容量只有 `textbox.mjs`，
   WebGAL 脚本转义只有 `production/src/script.mjs` 的 `escapeText`；编译器与生产层共用
   （六个特殊字符：`\` `;` `:` `|` `{` `}`，见 [`webgal-redlines.md`](webgal-redlines.md) §3.11）。

> ⚠️ **缺产物 / 缺配乐时的行为是「明确报错」，不是「静默降级」。**
> 缺 `mainline/*.json` → 打印三步恢复指引；`SCENE_CUE` 为空 → 列出「哪些场景没有配乐」。
> 这条是刻意设计的：静默降级在 VN 里的表现是**全场静音**或**画面空白**，比报错难查得多。

## 四、目录职责

| 目录 | 角色 |
|---|---|
| `compiler/` | 文字剧本编译链；切分、容量与内容锚点保持唯一实现 |
| `production/` | 演出组装、原生产物接驳、安装回退、本地服务、打包和验收 |
| `docs/` | 设计文档 |
| `webgal-tool/` | **上游 WebGAL 发行版，只读**，不修改不提交（自行下载） |
| `verify-repo.mjs`（仓库根） | 一键自检：依赖解析 / 真实加载 / 资源对齐 / 文档引用 |

---

## 五、协作纪律

1. 改架构 → **先改本文**，再改代码。
2. 交付前跑测试（`node verify-repo.mjs` + `compiler/test-screenplay.mjs` + `compiler/test-split.mjs`）。
3. **同一份规则只能有一处实现。**
4. 生成物必须能一键回到上游原样（可回滚的才是可实验的）。
5. **「演示跑通」≠「交付可用」**；换素材先看格式；「找不到」先确认找的地方对不对。
6. ★ **`node --check` 通过 ≠ 跑得起来**。它只查语法、**不解析 import**，
   缺依赖的文件照样「绿灯」。验「能不能加载」只有一个办法：**真起子进程去加载它**——
   这就是 `verify-repo.mjs` 存在的理由。
7. **移除代码前先算依赖闭包**，别按目录归属猜。猜会同时犯两种错：删多了，或删不干净。
8. 改了任何脚本之后，**至少跑一次 `node verify-repo.mjs`**。
9. 生产层使用稳定拍 ID 和正文摘要锁定演出配置；它不另写文字切分器，也不替代 `compiler/anchor.mjs` 的内容子串匹配。
10. 完整验证用根目录 `npm test` 与 `npm run check`。真实作品正文、素材、截图、原验收记录和密钥均不提交；示例必须可离线重建。
